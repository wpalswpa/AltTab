# PassFinder 구매 가정 점검

이 문서는 제출 전 사업 가정의 검토와 검증 계획이다. 요구사항은 [PRD](../PRD.md), 사업 설계는 [설계서](설계.md)가 정본이다. 이 문서는 상품·권한·구현을 변경하지 않는다. 검토 기준은 [PR #4](https://github.com/Snow0821/AltTab/pull/4)의 `720355f`다.

## 판단 기준

계속 묻는 질문은 “이걸로 사업이 되나?”다. 비용이 낮다는 사실과 학생이 돈을 낸다는 증거를 구분한다. 현재 구매 의향, 실제 결제, 반복 구매는 확인하지 않았다.

## 구매를 막는 조건

| 질문 | 코드·문서 근거 | 판단과 다음 행동 |
| --- | --- | --- |
| AI를 쓰는 한 명이 만들면 친구가 바로 풀 수 있나? | `lib/review.ts`는 작성자·본인 검수 통과·검증 완료 문항만 허용한다. `supabase/schema.sql`은 작성자 외 서로 다른 2명의 2차 통과가 있어야 검증 완료로 판정한다. | 1차 통과만 있는 과목에 참여한 일반 학생은 바로 풀 수 없다. 작성자 1명과 검수자 2명이 실제 검수한 체험 과목을 준비하고, 새 참여자 계정으로 확인해야 한다. 검수 조건을 몰래 완화하지 않는다. |
| 2,900원은 월 구독료인가? | `PRD.md` 9절과 `app/api/payments/route.ts`: 과목당 1회 2,900원, 모든 과목 30일 9,900원. | 월 2,900원 제안과 현재 구현은 다르다. 이 검토는 PR #4 상품을 유지한다. 최종 채택안을 하나로 맞춰야 한다. 결제는 모의이며 자동 갱신·매출 실적이 없다. |
| 3과목이면 구독이 저렴한가? | 2,900 × 3 = 8,700원, 2,900 × 4 = 11,600원. | 가격만 비교하면 4과목부터 9,900원이 저렴하다. 과목 이용권은 기간 제한이 없고 구독은 30일이라 단순 가격 외 기간 가치도 다르다. |
| 서버가 문제 생성비를 부담하나? | PRD 10절은 서버 생성형 LLM을 제외한다. `lib/embed.ts`는 임베딩을 호출하고 문항 생성은 사용자 AI에 맡긴다. | 사업자가 부담하는 생성 원가를 줄이는 대신 학생의 AI 사용량과 연결 시간을 요구한다. 비용 이전 자체는 구매 이유가 아니다. |
| 검수 인건비 0원이 곧 운영비 0원인가? | 설계서는 학생 AI 교차 검수를 쓰지만 문의·오류 대응 시간은 미측정이라고 적는다. | “운영자의 사전 전수 검수 단계를 두지 않는다”까지 설명할 수 있다. 오류 처리·지원·학생의 검수 시간을 포함한 총비용이 0원이라는 주장은 피한다. |
| 저렴한 문제 생성보다 더 살 이유가 있나? | 현재 상품은 같은 과목 문항 축적, 교차 검수 이력, 채점, 단계별 학습 진행을 제공하도록 설계됐다. | 실제 시험 범위와 문항 품질, 준비 시간 절약이 확인돼야 한다. AI 검수 통과는 정답 보증이나 학점 향상 증거가 아니다. |

## 원가와 수익 판단

과목 이용권의 기여이익은 결제액에서 적용 세금, 결제 수수료, 배분된 임베딩·저장·트래픽·지원 비용을 뺀 금액으로 계산한다. 영업이익은 여기에 고정 운영비·개발 유지비·고객 유입 비용까지 반영해야 한다. 가격 2,900원만으로 이익을 확정할 수 없다.

과목 이용권은 1회 결제이므로 활성 사용자 수를 월 구독 매출로 곱하지 않는다. 같은 과목 재방문은 사용 유지 지표이며 추가 매출이 아니다. 새 과목 구매·30일 이용권 재구매는 별도로 검증한다. 무료 이용자와 생성 기여자로 인해 발생한 사업자의 비용도 수익 계산에 포함한다.

## 다음 검증

1. 작성자와 서로 다른 검수자 2명이 체험 과목의 문항을 준비한다. 같은 개념·난이도의 출제 가능 문항이 5개 이상인지 확인한다.
2. AI 연결이 없는 새 참여자가 도움 없이 참여 코드 입력부터 첫 스테이지 종료까지 진행한다. 소요 시간, 멈춘 단계, 설명이 필요했던 횟수를 기록한다.
3. 팀 외 학생 3명에게 본인 교안 기준으로 기존 공부 방식과 비교하도록 요청한다. “좋다”는 평가 대신 무엇을 덜 했는지, 틀리거나 빠진 내용이 무엇인지 묻는다.
4. 과목 이용권의 범위·기간·가격을 정확히 설명한 뒤 구체적인 구매 이유와 거절 이유를 묻는다. 구매 의향을 실제 매출로 적지 않는다.
5. 같은 시험 기간에 다시 사용하는지 관찰한다. 첫 체험만으로 반복 사용을 주장하지 않는다.

세 명 관찰은 문제를 찾는 탐색이며 시장 수요를 입증하는 표본이 아니다. 사용자가 문제를 풀기까지 계속 안내가 필요하거나 자기 교안에 맞는 문항을 확보하지 못하면 기능 추가보다 이 경로를 먼저 고친다.

기록할 항목은 참여자 익명 번호, 사용한 과목·문항 수, 생성·검수 준비 시간, 첫 풀이까지 걸린 시간, 막힌 단계, 발견한 오류, 구매·거절 이유, 재방문·재구매 여부다. 관찰 전에는 빈칸으로 두고 예상 응답이나 가상 매출로 채우지 않는다.

현재의 중단·수정 기준은 다음과 같다. 새 참여자가 시작하지 못하면 먼저 검수된 문항 확보와 안내를 고친다. 초기 기여자가 생성·검수 부담을 계속 맡으려 하지 않으면 유입 가정을 재설계한다. 직접 공부할 때보다 줄어든 일이 없거나 다음 과목의 구매 이유가 없다면 가격 인하만으로 해결됐다고 보지 않는다.

## 검증 기록

- 기존 `npm test`: 17개 통과. 실제 DB·AI 연결·사용자 수요를 검증한 결과는 아니다.
- `node scripts/business-flow-check.mjs`: 6개 검사 통과. 실제 `lib/review.ts` 함수에 메모리 DB 대역을 연결했다. 1차 통과 문항 5개에서 새 참여자는 0개, 작성자는 5개를 풀 수 있었다. 본인이 검수한 사용자는 5개를 풀지만 별도 새 참여자는 여전히 0개였다. 검증 완료 상태에서는 새 참여자도 5개를 풀고, 숨김 상태에서는 작성자·검수자 모두 0개였다. 가격 비교도 확인했다.
- 검증 완료 상태는 대역이 공급한 값이다. 서로 다른 검수자 2명이라는 집계 조건은 SQL 소스로 확인했으며 실제 DB에서 실행하지 않았다.
- 문구 검사(`--scope 팀`): 오류 0건, 확인 0건. 제품 코드와 Claude의 작업 폴더는 수정하지 않았다.
- 실제 Supabase, 브라우저 학습 흐름, 유료 API, 결제는 이 검토에서 실행하지 않는다.

## 발표 답변 초안

“현재 구현에서는 학생의 AI가 문항을 생성하고, 저희 서버는 임베딩과 문제 저장·채점·진도 관리를 맡습니다. 학생이 만든 문항을 다른 학생이 활용하려면 정해진 검수 조건을 충족해야 합니다. 수익 가설은 과목별 학습 진행에 2,900원을 받는 것입니다. 낮은 생성 원가만으로 사업성을 주장하지 않고, AI 연결 없이 참여한 학생의 학습 시작 시간과 재사용·구매 의향을 확인하겠습니다.”
