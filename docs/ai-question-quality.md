# AI 문항 품질 검사 설계 (FR-12B 보강)

기준일 2026-10-03 · 브랜치 `fix/ai-question-quality` · 대상 `ai-generate.js`, `tests/ai-generate/`

[화면 설계](exam-workspace-ui.md)의 FR-12 절이 생성 API의 계약을 정의한다. 이 문서는 그 계약 안에서 문항의 **의미 검사**를 어떻게 하는지와 검증 기록을 둔다. 제품 요구사항 정본은 [PRD](../passfinder-prd.md)이며 여기서 바꾸지 않는다.

## 1. 문제

기존 `check()`는 보기 4개·정답 번호 0~3·해설 유무·근거 인용문이 고른 쪽에 있는지만 본다. 정답이 교안 기준으로 맞는지, 정답이 하나뿐인지, 해설이 정답과 같은 말을 하는지, 두 문항이 같은 내용인지는 보지 않는다.

재현(합성 사례, `tests/ai-generate/reproduce-current-check.test.mjs`, 2026-10-03 15:29 실행, 4/4 통과 = 4건 모두 검사를 그대로 통과):

| 사례 | 입력 | 기존 결과 |
| --- | --- | --- |
| 1 | 스택을 묻고 정답을 큐로 지정, 인용문은 진짜 | 통과 |
| 2 | 정답은 스택, 해설은 "정답은 큐다" | 통과 |
| 3 | 보기 `스택`·`LIFO 스택`을 따로 넣어 정답 둘 | 통과 |
| 4 | 같은 근거·같은 보기로 문장만 바꾼 두 문항 | 둘 다 통과 |

이 네 건은 검사 누락을 보여주려고 손으로 만든 입력이다. 실제 모델이 얼마나 자주 틀리는지를 뜻하지 않는다. 실제 비율은 7절의 평가를 실행해야 알 수 있다.

## 2. 검사 순서와 상한

```
요청 → 입력 검사(400) → [생성 호출] → 형식·근거·중복 검사(기존 + 보강)
     → [풀이 검토 호출: 정답·해설 숨김] → 정답 일치·단일 정답·근거 대조
     → [해설 검토 호출] → 해설이 가리키는 보기 = 정답
     → 5개 이상이면 200 / 모자라면 호출·시간 남을 때 한 번 더 생성 / 그래도 모자라면 422
```

| 항목 | 값 | 이유 |
| --- | --- | --- |
| 문항 수 | 5 (첫 생성은 7개 요청) | 기존 계약 유지. 검토에서 떨어질 여유 |
| 전체 제한 시간 | 110초, `GENERATE_DEADLINE_MS` | 생성 17~33초 실측 + 검토 2회. 남은 시간이 5초 미만이면 새 호출을 하지 않는다 |
| 호출당 제한 | 55초 또는 남은 시간 중 짧은 쪽, `KOOKMIN_CALL_TIMEOUT_MS` | 기존 55초 유지 |
| 최대 호출 수 | 6, `GENERATE_MAX_CALLS` | 생성 2 + 풀이 검토 2 + 해설 검토 2. 무한 재생성 금지 |
| 생성 라운드 | 최대 2 | 기존과 같음. 2라운드는 통과 문항을 피해 부족분+2개만 요청 |
| 검토 응답 형식 오류 | 같은 후보로 검토 1회 재시도, 또 실패하면 그 후보 전부 거절 | 검토 실패를 통과로 바꾸지 않는다 |
| 모델 | 기존 `KOOKMIN_MODEL`(기본 `claude-sonnet-5`) 하나 | 모델 교체·벡터 DB·새 프레임워크 없음 |

실패 동작(기존 계약 유지): 400 `invalid_input`, 503 `ai_not_configured`, 502 `ai_failed`, 504 `ai_timeout`(호출 하나가 제한을 넘김), 422 `not_enough_valid`(검토까지 통과한 문항이 5개 미만. `validCount`, `rejectedReasons` 포함). 시간·호출 상한에 걸려 멈춘 경우도 422이며 `rejectedReasons`에 `시간 제한`·`호출 횟수 제한`이 들어간다. 실패 응답에 문항을 넣지 않는다.

성공 응답은 기존 필드(`ok, source, model, generatedAt, questions[5], rejectedCount`)를 그대로 두고 `review`를 더한다: `{ method: "same-model-blind-solve", model, reviewed, calls, elapsedMs }`. 문항에는 `concept`, `type`(정의·비교·적용)이 더 붙는다. 클라이언트(`make.mjs`)와 세트 저장(`exam.js`)은 이 필드를 무시해도 동작한다.

같은 모델을 다시 부르는 검토이므로 "독립 모델 검증"이나 "정답 검증 완료"라고 쓰지 않는다. 응답의 `review.method` 값과 문서에서 모두 "같은 모델의 별도 풀이 검토"로 부른다.

## 3. 형식·근거·중복 검사(비용 없음)

기존 검사에 더한 것:

| 검사 | 거절 사유 | 잡는 사례 |
| --- | --- | --- |
| 보기 하나(공백 제거 2자 이상)가 다른 보기에 그대로 포함 | `보기가 서로 포함` | 3 (`스택` ⊂ `LIFO 스택`) |
| 통과한 문항과 근거 인용문이 같음 | `같은 근거 반복` | 4 |
| 통과한 문항과 보기 4개가 집합으로 같음 | `같은 보기 반복` | 4 |
| 통과한 문항과 문제 문장의 글자 2그램 자카드 유사도 0.6 이상 | `비슷한 문제` | 문장만 조금 바꾼 반복 |
| 통과한 문항과 `concept`이 같음 | `같은 개념 반복` | 개념 배분 어김 |

1자 보기(`n`, `2n`)는 포함 검사에서 뺀다. 사례 1·2(정답 오류, 해설 모순)는 글자 검사로 잡을 수 없어 4절의 검토 호출이 맡는다.

## 4. 풀이 검토와 해설 검토(호출 2회)

풀이 검토 입력: 교안 쪽 원문 + 각 후보의 `id, body, choices`. 생성된 `answer_index`, `explanation`, `evidence`는 넣지 않는다. 지시: "교안만 근거로 각 문제를 풀어라. 정답이 하나뿐인지 판단하고, 보기마다 맞음/틀림/판단불가를 적어라. 근거는 교안 문장을 그대로 복사하라."

반환 구조(JSON):

```json
{"results":[{"id":"c1","single_answer":true,"chosen":1,"evidence_quote":"교안 원문","per_choice":[{"index":0,"verdict":"wrong","reason":"..."},...]}]}
```

채택 규칙(하나라도 어기면 거절):

| 조건 | 거절 사유 |
| --- | --- |
| 후보 id가 결과에 없음 | `검토 누락` |
| `chosen`이 0~3 정수가 아니거나 `per_choice`가 4개가 아님 | `검토 응답 오류` |
| `single_answer !== true` | `검토: 단일 정답 아님` |
| `chosen !== answerIndex` | `검토 정답 불일치` |
| 정답 외 보기의 `verdict`가 `correct` | `검토: 복수 정답` |
| 정답 보기의 `verdict`가 `correct`가 아님 | `검토: 정답 확신 부족` |
| `evidence_quote`(공백 제거 10자 이상)가 고른 쪽 어디에도 없음 | `검토 근거 부족` |

해설 검토 입력: 교안 + 풀이 검토를 통과한 후보의 `id, body, choices, explanation`(정답 번호는 숨김). 지시: "이 해설이 정답이라고 설명하는 보기 번호를 적고, 해설 내용이 교안과 어긋나면 `consistent:false`." 반환 `{ "results": [{ "id", "explanation_answer_index", "consistent", "reason" }] }`. 번호가 생성 정답과 다르면 `해설이 다른 보기를 가리킴`, `consistent !== true`면 `해설이 교안과 어긋남`, 없으면 `해설 검토 누락`.

검토도 틀릴 수 있다. 검토가 거절한 문항은 응답에 넣지 않지만 "오답"으로 확정하지도 않는다. 사람 표본 평가(7절)가 검토의 오판 비율을 따로 본다.

## 5. 출제 배분(검토 다음 우선순위)

생성 프롬프트에 두 단계를 넣는다. ① 고른 범위에서 서로 다른 핵심 개념을 먼저 뽑는다(교안에 있는 것만). ② 개념당 문항 1개를 배정하고 유형을 섞는다: 정의(용어·성질을 묻기), 비교(교안에 함께 설명된 두 개념의 차이), 적용(교안에 적힌 규칙·절차·예시를 그대로 적용하면 답이 정해지는 상황). 7개 요청 기준 정의 3·비교 2·적용 2를 목표로 하되 교안에 비교·적용의 근거가 없으면 정의로 대신한다. 교안 밖 지식, 억지 난도 올리기, 계산 문제 만들기를 금지한다. 출력 JSON에 `concept`, `type`을 넣고 3절의 `같은 개념 반복` 검사로 배분을 강제한다. 유형은 검사하지 않고 응답에 그대로 둔다(평가 자료용).

## 6. 비용 없는 회귀 테스트

`node --test tests/ai-generate/` 로 실행한다. 학교 AI 대신 테스트 안에서 띄운 가짜 `/v1/messages` 서버를 `KOOKMIN_BASE_URL`로 가리켜 실제 fetch 경로·타임아웃·JSON 처리를 그대로 탄다. 가짜 응답으로 검사 흐름을 확인하는 것이지 모델 품질을 재는 것이 아니다.

| 파일 | 확인하는 것 |
| --- | --- |
| `reproduce-current-check.test.mjs` | 1절의 재현 기록(기존 `check` 동작, 사례 1·2는 글자 검사로 못 잡음을 그대로 둠) |
| `check.test.mjs` | 3절 검사: 보기 포함, 같은 근거, 같은 보기, 비슷한 문제, 같은 개념, 1자 보기 예외, 기존 검사 유지 |
| `pipeline.test.mjs` | 정상 5문항(응답 계약·`review`), 잘못된 정답, 복수 정답, 근거 부족, 모순 해설, 검토 누락, 검토 JSON 오류 재시도 뒤 거절, 생성 JSON 오류, 호출 타임아웃 504, 전체 제한 시간, 최대 호출 수, 5문항 미달 422, 키 없음 503, 502 오류, 입력 400 |

## 7. 고정 평가 자료와 실행 도구(유료 호출)

- 자료: `tests/ai-generate/fixtures/*.json`. 팀이 직접 쓴 짧은 교안이다. `tuning`(프롬프트 손볼 때만 씀)과 `eval`(최종 측정)로 나눈다.
- 도구: `node tests/ai-generate/eval-live.mjs --estimate` 는 호출 수·토큰·비용 추정만 출력한다. `--run --max-usd <승인액>` 과 서버 환경의 `KOOKMIN_KEY`가 있을 때만 실제 호출하며, 추정 비용이 승인액을 넘으면 시작하지 않는다. 결과는 `tests/ai-generate/eval-results/<시각>.json`과 사람 평가용 CSV로 남긴다.
- 기록 항목: 요청별 성공/실패, 걸린 시간, 호출 수, 거절 사유, 문항별 `concept`·`type`, 검토 결과. 정답 정확성·단일 정답·근거 충분성·해설·중복은 CSV의 사람 판정 칸이 비어 있는 동안 **미확인**이다. 생성 모델이나 검토 모델의 판단을 정답표로 쓰지 않는다.
- 목표 표본 30~50문항(요청 6~10건). 실제 확보량과 분모를 보고한다.

### 실행 여부

이 브랜치 작업 중 실제 학교 AI 호출은 **0회**다. 이 환경에 `KOOKMIN_KEY`가 없고 호출 예산 승인이 없다. 추정값은 `--estimate` 출력으로 갱신한다.

## 9. 남은 일

- 호출 예산 승인 뒤 `eval-live.mjs --run` 실행, CSV 사람 판정, 결과를 이 문서 8절에 분모와 함께 기록.
- 검토 호출이 더해져 요청 시간이 늘어난다. 화면 문구 "최대 1분"은 UI 담당 몫이며 실측 뒤 조정한다.
- 배포 환경의 함수 실행 시간 상한은 확인하지 않았다. 110초가 길면 `GENERATE_DEADLINE_MS`로 줄인다.
- PRD 6절의 "최대 한 번의 추가 호출" 문장은 이 브랜치가 main에 들어가면 "호출 최대 6회·110초"로 한 줄 바꿔야 한다. PRD 동결 원칙에 따라 통합 결정 때 같이 고친다.
